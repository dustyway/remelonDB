# v0.3.0

Blob columns add binary data that lives in a row and travels through sync. Local-only tables add queryable device storage that sync ignores. This release also carries sync-engine, server, and web-broker fixes from a full review of the store, broker, and push pipeline. Every package moves to 0.3.0 together.

## Upgrading

- **`@remelondb/driver-rn-cpp` requires React Native 0.86 or newer.** Blob binding uses the typed-array API in 0.86's JSI runtime. Apps on 0.80 to 0.85 stay on 0.2.6 of this driver or upgrade React Native. `@remelondb/driver-rn` with expo-sqlite is unaffected.
- **`zod` is pinned to `~4.4.3`.** The Zod adapter identifies blob schemas through Zod internals that carry no stability promise, so the peer range names the versions this release was tested against. Apps that already resolve a 4.4.x Zod need no change. Zod 4.5 or later fails peer resolution until a remelonDB release lifts the pin.
- Created records still start as `_status: 'created', _changed: ''`, but later edits now accumulate column names in `_changed` while the status remains `created`. This lets an accepted push whose local mark was interrupted reconcile newer server values without losing edits made after the push snapshot. Code that reads internal bookkeeping fields may observe the new column list.
- Integer-valued numbers outside JavaScript's safe range are rejected during record sanitization. SQLite can store them, but JavaScript cannot read them back exactly. Use a string column for larger integers.
- Hand-written HTTP bindings that use blob columns validate decoded engine rows with `wire.localRows`, not `wire.rows`, and encode `wire.pullResult` or `wire.pushResult` before serializing JSON. `@remelondb/nestjs` performs both steps automatically.

## Added

- **`column.blob()`** stores a `Uint8Array` as a SQLite BLOB, with `.optional()` for nullable columns. The record type infers `Uint8Array`, and `null` when optional. Blob columns cannot be indexed, sorted on, or used in `Q` clauses, including inside `Q.on`. The type system refuses the column name and the collection throws at query time. Sanitization copies the caller's array, so mutating the original after `create` or `update` does not change the cached record. Reads return the stored array, which callers must treat as read-only. An `addColumns` migration backfills a required blob with a zero-length value. Details are in [docs/reference/schema.md](../reference/schema.md) and [docs/reference/records.md](../reference/records.md).
- **`table(..., { localOnly: true })`** creates an ordinary queryable and migratable table that the sync layer never pushes, pulls, or clears during replacement sync. Local-only deletes are permanent rather than tombstoned. This is intended for device caches such as downloaded media.
- **Blobs on the sync wire** use padded canonical base64 inside the JSON record. Core encodes on push and decodes on pull, so transports never see bytes. `syncSchemas` maps a `z.instanceof(Uint8Array)` field to a base64 codec on the wire and keeps the app's refinements. The NestJS module encodes pull responses and decodes push bodies. The Drizzle store gains a `bytea` column type. The wire contract is in [docs/sync-wire.md](../sync-wire.md).
- **`zodTable` accepts `z.instanceof(Uint8Array)`**, optionally `.nullable()`, and refuses `indexed` on such a column.
- **`Database.open({ randomSource })`** replaces the ambient `crypto.getRandomValues` for every id the database mints. The open-time probe exercises it, `database.randomId()` covers app-side minting, and the global stays the default. The source contract is synchronous. It fills the given array and returns it. An async source fails at open instead of minting identical ids from a zeroed buffer. React Native apps can pass expo-crypto's `getRandomValues` instead of installing a global shim.

## Fixed: sync and server

- A remote creation over a local tombstone destroyed the pending delete and resurrected the row with nothing left dirty. The local tombstone now stands, matching the updated bucket and resync paths.
- A remote row over a locally created record replaced every column, and the next push sent the server's values back as this client's creation. Local creations now keep their values, and the conflict resolver is still consulted.
- A pushed creation left dirty by an interrupted mark now accepts later server updates while preserving columns edited locally after the push snapshot.
- Pushed tombstones gained the gate other rows already had. The client destroys a row after push only if it is still a tombstone. Another context can destroy the tombstone and recreate the id mid-push, and the old behavior erased that newer row.
- The client reconfirms its sync turn before the write that destroys local state. The old path acquired the turn once per run even though the web driver's lease lasts ten seconds, so a slow push could hand sync ownership to a second tab.
- Replacement sync now applies only tables present in the response. Omitted tables retain their rows, matching the wire rule that an absent table means no changes. A response that names a local-only table is rejected in normal and replacement modes.
- Pull normalization deduplicates repeated deletion ids, so one remote deletion produces one operation and one observer notification.
- The server checks staleness before validation for every requested record in scope. A stale record answers `conflict` even when validation would reject its value. Push interleave exclusion is keyed by table and id, so pushing an id in one table no longer hides the same id's changes in another. A cursor beyond the server's horizon is a conflict. Conformance checklist items 19 and 20 cover both cases.
- Invalid ids returned by a server cross-validation hook produce server errors. Client-originated malformed protocol requests remain `SyncProtocolError` failures.
- Drizzle `upsert` never touches another scope's row. The memory store serializes push transactions per scope. Tombstone garbage collection prunes to a fixpoint with per-table savepoints, so a foreign key between synced tables skips a pass instead of blocking collection.
- Memory and reference stores reject invalid garbage-collection floors before `NaN` or `Infinity` can poison issued cursors.

## Fixed: driver-web

- A failed cold open undoes its holder instead of poisoning the name for the broker's life.
- Only a slot's owner can release it. A guessed id no longer puts two tabs inside exclusive write blocks.
- Sync leases clamp to a five-minute ceiling, so one tab's `Infinity` cannot block sync ownership indefinitely.
- Holders remember their storage kind. An epoch reset restores a memory database as memory, and a joiner asking for the other kind is refused instead of silently attached. SharedWorker storage-kind mismatches now reject `open()` rather than resolving with an error-shaped success.
- Stranded requests replay from the front of the backlog in their original order, so a query no longer replays before the open it depends on. A tab asked to spawn twice terminates its previous worker.
- Cross-tab updates from an older schema no longer replace newer cached columns with defaults. Blob-bearing queries compare bytes rather than `Uint8Array` identity, avoiding duplicate emissions for bookkeeping-only broadcasts.
- Closing after another tab destroys the database now completes normally.

## Fixed: runtime

- The NestJS runtime awaits scopes passed directly to `pull()` and `push()`, preventing a Promise object from becoming a tenant key in custom controllers.
- Live observation failures without `onError` remain unhandled promise rejections rather than timer exceptions. Discarded observations remain quiet.

## Changed

- `SqlValue` at the driver seam includes `Uint8Array`. Custom drivers bind it as a BLOB and return BLOB columns as `Uint8Array`. The Node driver returns a plain view over better-sqlite3's `Buffer`, since `Buffer` has its own `toJSON`.
- Blob base64 uses the host's `atob` and `btoa`, present on Node, browsers, and Hermes at the versions this release supports.

## Tests

- The driver conformance suite gains a blob round trip through create, update, query, and delete. It passed on Node, sqlite-wasm in Chromium, Firefox, and WebKit, and the C++ TurboModule on the Android emulator.
- A blob row syncs between two Node databases through the reference server byte-identical, and through the NestJS module with a PostgreSQL `bytea` column.
- Local-only tables are covered for querying, migration, sync exclusion, replacement sync, and local deletion.
- Multi-tab behavior is exercised in the browser suite and its Quint model. Sync behavior remains covered by the server conformance suite and `docs/sync_model.qnt`.
- The repository lints under `strictTypeChecked` at error level.

## Docs

- Base64 grows bytes by 4/3, and a push carries every dirty row. A body over the host's parser limit, 100 KB by default in NestJS, fails with 413 and retries the same batch on every sync. A per-column cap cannot bound a batch. `docs/sync-wire.md` and the NestJS README state the limit and the app-side byte validation that prevents it.
- Synced blobs suit bounded payloads. For large media, store the bytes in object storage, sync a stable key and metadata, and use a local-only table as the device cache. [The sync reference](../reference/sync.md#binary-payloads) covers the tradeoff and upload lifecycle.
- The C++ driver README and `docs/reference/runtimes.md` state the React Native 0.86 floor.
