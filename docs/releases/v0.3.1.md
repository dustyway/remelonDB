# v0.3.1

A driver-web patch release. Firefox could leave a page stuck on opening after the machine slept and woke: the broker's compute worker died or froze while Firefox kept its OPFS sync access handles, and every later `open()` retried the locked pool forever. Every package moves to 0.3.1 together; no other package changes.

## Upgrading

- No API changes. `@remelondb/driver-web` exports a new `OpfsPoolHeldError`; apps that catch open errors can show a Retry that reopens, and advise a browser restart when it persists.

## Fixed: driver-web

- A held OPFS pool is reported instead of retried forever. `open()` retries a transient pool lock with bounded backoff (about four seconds in total, inside the default 15 s open timeout) and then rejects with a typed `OpfsPoolHeldError` (`code: 'OPFS_POOL_HELD'`) whose `diagnostic` keeps the browser's final `NoModificationAllowedError`. Before, the retry ladder ran past the open timeout and the app saw only the generic timeout.
- The broker releases its own OPFS pool before replacing a silent compute worker. A new `releasePool` worker op closes every database and pauses the SAH-pool VFS, so the handles come free before the worker is terminated. A worker that does not answer within four seconds still falls through to the hard reset. On Firefox, terminating a worker after resume otherwise leaves its handles locked for the rest of the browser session.
- After an idle release the driver restarts on its own instead of staying retired.
- The typed error survives the broker boundary: a shared-mode caller receives `OpfsPoolHeldError`, not a plain `Error` with the message, and before its own open deadline.
- The broker logs why it fell back from the shared-worker host to the tab host (`[remelonDB] shared worker could not host compute (...)`), and logs which host it chose.

## Tests

- `poolHeld.test.ts` pins that the retry ladder finishes before the default open timeout, that a held pool stops retrying with the browser diagnostic retained, and that `releasePool` closes databases before pausing the pool. `poolHeld.browser.test.ts` checks the typed error reaches a shared-mode caller before its deadline.
- Playwright's Firefox does not reproduce the suspend/resume path, so `staging-acceptance.mjs` documents the manual check: load the app in Firefox, let the machine sleep, wake it, reload; no pool-held error should appear. Verified on NAC staging with the 0.3.1-dev prereleases (dustyway/remelonDB#49).
