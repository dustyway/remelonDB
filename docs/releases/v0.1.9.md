# v0.1.9

Feature release closing the six-issue backlog (#7–#12). All packages
move to 0.1.9 in lockstep. Every feature landed test-first; the suite
grew by 14 tests plus a compile-time type-test file.

## Added (core)

- `synchronize()` returns a structured result (#9):
  `{ lease, resynced, pulled, pushed, rejected, retryCount }`.
  Callers branch on data instead of parsing log lines — the log
  wording is no longer load-bearing anywhere. Existing callers that
  ignore the resolved value are unaffected. Semantics: `pulled` counts
  remote rows applied (pull phases plus interleaved push changes),
  `pushed` is rows the server accepted, `rejected` is per-record
  rejections, `retryCount` is extra rounds forced by push conflicts,
  and `lease: 'unavailable'` means another context held the sync lease
  and nothing ran.
- `synchronize({ signal })` accepts an AbortSignal (#10). It cancels
  between protocol phases — never inside a write, so a transaction is
  never left half-applied — and is passed to `pullChanges`/
  `pushChanges` as a second argument so transports can cancel in-flight
  requests. Wire it to logout/dispose to stop a sync from outliving its
  owner.
- Prepared delete operations (#7): `prepareMarkAsDeleted` and
  `prepareDestroyPermanently` on Collection and Model. A parent-and-
  children delete cascade now commits as one `db.batch()` transaction —
  one commit, one notification, one cross-tab broadcast, and a mid-batch
  failure applies nothing. `markAsDeleted`/`destroyPermanently` route
  through the same builders.

## Clarified (core)

- The `db.write()` contract is now stated explicitly in the docstring
  and tutorial (#7): it is a serialized writer window, not a
  transaction. Each `create`/`update`/delete inside commits on its own;
  `db.batch()` is the atomic unit. This documents existing behavior —
  nothing changed at runtime.

## Added (server)

- `crossValidateChanges` (#8): a cross-record validation hook that
  receives the full proposed change set per table — upserts _and_
  deletions — so referential rules can reject a delete (e.g. a parent
  with surviving children). Returned ids are rejected whichever kind
  they name, before anything mutates. The rows-only `crossValidate`
  remains supported; both may run and their rejections merge.
- Behavior note: a legacy `crossValidate` rejection now also drops a
  same-id deletion from the request instead of half-applying an id the
  hook rejected.

## Added (nestjs)

- `syncEngineFromOptions(config)` (#11): builds exactly the engine
  `RemelonSyncModule` would build, from the same options minus
  `scopeFrom`. Share one config object between direct construction
  (tests, scripts) and `forRoot`/`forRootAsync` and the two paths
  cannot drift. Covered by a test running the same assertions against
  a direct engine and the module over real HTTP.

## Added (store-drizzle)

- `drizzleSyncTable<Scope, Table>(config)` (#12): a schema-aware config
  builder. `scrub` keys and value types are checked against the table's
  insert model and `insertOnly` against its real column names, at
  compile time. A plain typed Drizzle schema and typed database now
  configure `createDrizzleStore` with no casts; the tsc-run type-test
  file in the package is the proof.

## Documentation

- `docs/codebase-guide.md`: a maintainer guide to the whole codebase,
  cover to cover, with each concept taught inline and a chapter on the
  NotAnotherCards consumer integration. Renderable to PDF (command in
  the file header). Updated for the 0.1.9 surface.
