# v0.2.4

Fixes a logout/re-login race where a manager's `close()` could resolve while a database it opened was still being torn down. No signature changes, though `init()` now rejects in two cases it previously did not; all packages move in lockstep.

## Fixed (core)

- `DatabaseManager.close()` resolved as soon as it had cleared its own state, even when an `init()` it owned was still running (#40). The database that open produced was closed on arrival, but through a detached `driver.close()` that nothing could wait for. An owner that awaited `close()` and then opened the same file — a logout followed by a login as the same account, or a React effect tearing down and setting up again — raced that teardown, and no amount of application-side sequencing could fix it, because the promise was discarded inside the library.
- The late arrival's teardown is now awaited before `init()` rejects, and `close()` waits for the `init()` it superseded to settle. Awaiting `close()` therefore means nothing the manager opened is still open, which is what lets an owner safely create the replacement. A failure closing that late database rejects `close()` rather than reporting a clean teardown; the superseded `init()` keeps reporting its own `closed during initialization` error.
- Concurrent `close()` calls share one teardown and close the driver once. A teardown that failed is kept rather than released, so a later `close()` reports it instead of answering with a clean resolve the manager cannot back up.
- `init()` now rejects while a close is running, and for good once a close has failed. Opening during a teardown would ask the manager to sequence itself against it, and reopening after a failed teardown would leave the next `close()` answering with the old failure while a new database stayed open. A close that succeeded still returns the manager to `idle`, so the documented re-login path is unchanged.

## Docs

- The database reference now states what closing guarantees, and that a manager does not coordinate with other managers — where two can address one database, the code owning them sequences the replacement.
- The multi-account section of the tutorial notes that `close()` waits for a discarded open's cleanup, so awaiting it means the file is released.

## Not covered

- Work already queued on the database is not drained before the driver closes, and `Query.fetch`, `localStorage`, and the sync helpers reach the driver outside that queue in any case. A read in flight when `close()` is called still fails with the driver's error. Tracked separately.
