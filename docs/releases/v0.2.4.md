# v0.2.4

Two fixes to closing a database. A manager's `close()` could resolve while a database it opened was still being torn down, and closing abandoned work the database had already accepted. Both mattered most on logout followed by a login as the same account. No signature changes to existing APIs — `Database.close()` is additive — though `init()` now rejects in two cases it previously did not; all packages move in lockstep.

## Fixed (core)

- `DatabaseManager.close()` resolved as soon as it had cleared its own state, even when an `init()` it owned was still running (#40). The database that open produced was closed on arrival, but through a detached `driver.close()` that nothing could wait for. An owner that awaited `close()` and then opened the same file — a logout followed by a login as the same account, or a React effect tearing down and setting up again — raced that teardown, and no amount of application-side sequencing could fix it, because the promise was discarded inside the library.
- The late arrival's teardown is now awaited before `init()` rejects, and `close()` waits for the `init()` it superseded to settle. Awaiting `close()` therefore means nothing the manager opened is still open, which is what lets an owner safely create the replacement. A failure closing that late database rejects `close()` rather than reporting a clean teardown; the superseded `init()` keeps reporting its own `closed during initialization` error.
- Concurrent `close()` calls share one teardown and close the driver once. A teardown that failed is kept rather than released, so a later `close()` reports it instead of answering with a clean resolve the manager cannot back up.
- Closing a database abandoned the work it had already accepted (#41). `DatabaseManager.close()` called `driver.close()` directly, so a `read` or `write` block accepted moments earlier — including one still waiting on the driver's cross-context work slot, which is invisible to the queue — could be running when the handle went away, and failed with whatever the driver says about a closed connection. `Database.close()` is new and additive: it refuses new reads, writes, and external-change applies, drains what was accepted, then closes the driver, and the manager closes through it. Core-owned driver work outside the queue (the query behind a fetch, `db.localStorage`, the sync helpers) is drained in a second phase, so a call issued from inside an accepted block still completes. Application code holding `database.driver` is outside the guarantee, and a close stays pending as long as a driver operation does.
- `init()` now rejects while a close is running, and for good once a close has failed. Opening during a teardown would ask the manager to sequence itself against it, and reopening after a failed teardown would leave the next `close()` answering with the old failure while a new database stayed open. A close that succeeded still returns the manager to `idle`, so the documented re-login path is unchanged.

## Upgrading

- Await `close()` before opening the same database again. `init()` on a manager whose close is still running now rejects instead of opening a second database that races the teardown, which is what it silently did before. Code that already awaited `close()` is unaffected: a close that succeeded returns the manager to `idle`, and `init()` opens fresh.
- A manager whose close *failed* is spent. Await the close, then replace the manager rather than reopening through it.
- `close()` can now take as long as an in-flight open does, where it used to return at once. On a driver whose open never settles, that is a wait rather than an early resolve that was not true.

## Docs

- The database reference now states what closing guarantees, and that a manager does not coordinate with other managers — where two can address one database, the code owning them sequences the replacement.
- The multi-account section of the tutorial notes that `close()` waits for a discarded open's cleanup, so awaiting it means the file is released.

## Not covered

- Application code that holds `database.driver` and calls it directly is outside the drain: core cannot see that work. Use `db.read` / `db.write`, or accept that such a call can race a close.
