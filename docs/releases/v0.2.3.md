# v0.2.3

Fixes a shared-mode failure where losing the compute worker during a page load could leave the database unreachable until the browser discarded the broker. No API changes; all packages move in lockstep.

## Fixed (driver-web)

- Shared mode could stop serving a database after a full page load, cleared only by a manual refresh (#38). On Chromium and WebKit the broker cannot construct the compute worker itself, so it asks a tab to host one. It asked the oldest pending route's port, which after a page load belongs to the page that just died, and `postMessage` to a dead port neither throws nor arrives. The broker recorded the request as sent and waited for a worker nobody was building, while the guard on the other recruitment path refused to ask the live page that had just arrived. Requests then rode out the 15 second open deadline, and any reaching a stale connection answered `database '…' is not open`.
- Recruitment now runs through one path with a deadline per candidate. The port that just sent a message is asked first, then the most recently connected ports; a candidate silent past its deadline is passed over, and a page connecting while a request is outstanding is asked as well. When every candidate has gone quiet the queued requests fail with that reason instead of hanging.
- State recorded before the worker confirms an operation is now rolled back when it fails. A cold open registers its holder eagerly, so a terminal recruitment failure used to leave that holder behind, and the next open for the same name would take the join path and ask a fresh compute for a database it had never opened.
- A worker adopted after another tab won the race is refused and its host told to discard it, rather than stranding a second compute holding the OPFS pool handles. Broker self-hosting, the Firefox path, no longer retries after its worker fails to load, which used to spawn replacements in a loop.
- The open-timeout message no longer presents bundler configuration as the likely cause. A lost compute host comes first, since a correct Vite setup produced this message throughout the reported failure.

## Docs

- The compute-recovery account in the codebase guide, `docs/multi-tab.md`, and the broker's header comment described behaviour that predates 0.1.x, where a lost compute failed every in-flight request and cleared holders. Requests have been requeued and holders kept since then.
- The control-message protocol is typed in `protocol.ts` for both directions and documented in the driver README and `docs/multi-tab.md`, which counted two messages where there are three.
