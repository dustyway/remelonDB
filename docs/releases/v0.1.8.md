# v0.1.8

Resilience release. All packages move to 0.1.8 in lockstep; the
substantive changes are in `@remelondb/driver-web`. Diagnosed against a
live Firefox deployment through the `0.1.8-dev.0/1` prereleases (those
carried temporary instrumentation and should not be used).

## Fixed (driver-web)

Opening the database no longer fails opaquely — or, in shared mode,
respawn-loops — when the browser blocks OPFS.

In Firefox **private browsing / "never remember history"** (and with
blocked site data), `navigator.storage.getDirectory()` throws a
`SecurityError` even over https, so OPFS is unavailable. Previously the
driver spawned a compute worker that could only fail; the shared-worker
broker then mistook the storage-denied worker for a dead one and
respawn-looped, surfacing a cryptic `database '<name>' is not open`.

Two changes fix this:

- **Fail fast, up front.** `open()` probes OPFS before any worker/broker
  spawns (`getDirectory()` throws on the main thread too in a denied
  context) and rejects with a typed error — no doomed startup, no loop.
  The probe is a no-op where OPFS cannot be probed (e.g. Node), so
  existing behavior is unchanged.
- **Liveness is answered out-of-band.** The compute worker now replies to
  the broker's `ping` immediately, without queuing it behind real work.
  A stalled op (e.g. a pool install retrying a transient error for
  seconds) can no longer make a busy-but-alive worker look dead and trip
  the broker's "went away" respawn.

## Added (driver-web)

- **`OpfsUnavailableError`** (`code: 'OPFS_UNAVAILABLE'`) — the typed
  rejection from `open()` when OPFS is blocked. Catch it (or check the
  `code`) to degrade gracefully: show a clear message, or reopen with
  `storage: 'memory'`, instead of treating it as a generic failure.
- **`probeOpfs(storage)`** — the exported availability check, for callers
  that want to detect OPFS support before opening.
