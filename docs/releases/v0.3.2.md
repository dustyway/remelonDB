# v0.3.2

A core patch release. `SyncController.syncNow()` returned nothing, so an app that awaited it to act on freshly synced data continued while the sync was still running. It now resolves with the run's outcome. Every package moves to 0.3.2 together; no other package changes.

## Upgrading

- `syncNow()` returns `Promise<SyncControllerState>` instead of `void`. Existing callers compile unchanged; with `no-floating-promises`, await it or mark it `void controller.syncNow()`.
- `status: 'idle'` means the run finished, not that every row was accepted. Rejected rows are in `state.lastResult`; check them where the UI reports success.

## Added: core

- `await controller.syncNow()` waits for the run it asked for and resolves with the controller's state, never rejecting: `idle`, `resync-required`, `offline` or `error`, with `error` set. Called while a run is in flight, it waits for the queued follow-up, so the caller sees data at least as fresh as the moment it called; calls during one run share that follow-up. After `dispose()`, pending calls resolve with the current state, which is still `syncing` when a run was in flight (dustyway/remelonDB#70).

## Fixed: core

- A `runSync` that throws synchronously no longer leaves the controller marked as running. The failure becomes the run's state, and later syncs run again; before, the controller never synced again.

## Tests

- `controller.test.ts` pins that `syncNow` resolves after a successful run with the result, that calls during a run share its follow-up while each run returns its own outcome, that a synchronous `runSync` failure resolves with an error outcome, that disposal resolves active and queued waiters even when the run ignores abort, that a disposed idle controller resolves at once without syncing, and that `notifyLocalWrite` still returns `undefined`.
